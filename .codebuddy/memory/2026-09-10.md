## 只读深挖 SOF wedge 根因（sudo 探测，未改任何配置）
- **确认加载配置**（来自 `/sys/kernel/debug/sof/fw_profile/`）：fw=`sof-adl.ri`、ipc_type=`0`(IPC3)、tplg=`sof-adl-es8336-dmic2ch-ssp0.tplg`。
- **固件版本**：`2:2:0-57864`；**Firmware ABI 3:22:1 / Kernel ABI 3:23:1 → ABI 小版本不匹配（22 vs 23），固件偏旧**（固件来自 `linux-firmware` 包 `20250310...deepin17`）。
- **wedge 性质**：`fw_state`/`exception`/`stream`/`debug` 全空，`etrace` 是二进制需 `sof-logger`（本机未装）→ 固件是 **IPC 挂死(hang) 而非 panic**（无异常回溯）。debugfs 在 wedged 态完全失能，无法就地恢复，只能重载固件。
- **触发线索强烈指向 DMIC**：首次 IPC timeout 在 09:05 的 `pcm1 (DMIC) dir 1`（捕获），10:15 后才蔓延到 `pcm0 (ES8336) dir 0`（播放）。当前 tplg 带 `dmic2ch`，本机模拟麦走 es8336 的 Differential Mux（我们的修复），**根本不需要 DMIC**。
- **候选防触发 topology（无 dmic）**：`sof-adl-es8336-ssp0/ssp1/ssp2.tplg.zst` 均存在。
- `snd_sof` 真实可用参数：`ipc_type`(0/1)、`ipc4_ignore_cpc`(关固件时钟缩放)、`tplg_filename`、`fw_filename`、`disable_function_topology`、`sof_debug`。`snd_intel_dspcfg.dsp_driver` 可切 1=legacy(会丢声)/4=AVS。
- 本机无 `/sys/bus/pci/devices/0000:00:1f.3/reset`，恢复只能走 unbind/bind 或重启；debugfs 有可写 `skip_imr_boot`（跳过固件 IMR，配合重启，若 IMR 损坏可用）。

### 结论性方向（按置信度）
- **防（最推荐，可逆、低风险）**：强制非 dmic topology `snd_sof.tplg_filename=sof-adl-es8336-ssp1.tplg`，直接去掉疑似触发源的 DMIC 管线；模拟麦路由修复不受影响。
- **防（根治期望高）**：更新 `linux-firmware` 拿 ABI 3:23:1 匹配的 sof-adl.ri；或更新 rolling 内核。
- **防（换通路）**：`snd_sof.ipc_type=1 snd_sof.ipc4_ignore_cpc=1`（IPC4 + 关时钟缩放）+ 配套 IPC4 tplg。
- **恢复**：重启（临时）/ PCI unbind+bind（折中，需实测）/ 看门狗自动恢复 / `skip_imr_boot`+重启。
- 用户要求：仅探索不修改。尚未落地任何改动。

## 架构决策：能否并入服务/自动检测（2026-09-10）
- 用户问"并入自动执行和检测脚本？由服务控制？"。结论：**拓扑参数不能由运行期服务控制**。
- 生命周期差异：UCM/Differential Mux 是运行时 mixer 控件，可由服务管（且 `huawei-speaker-mute.sh` 已在做）；强制 ssp0 无 DMIC 拓扑是内核模块参数，仅模块加载时读一次，运行期改它必须重载 snd_sof → 丢设备（用户已验证）。服务在模块加载后才起，碰不到拓扑。
- 正确结构：① 拓扑参数 + UCM 修正放进 `install.sh` 作一次性开机静态配置；② 服务只管插拔监听/功放软静音/Differential Mux 保证；③ "检测"看门狗 = 服务扫 dmesg 找 IPC timeout。
- **看门狗最终定案（2026-09-10 用户修正）：不自动重启，改为系统通知（notify-send）提醒用户手动重启，且仅通知一次（用 /run 哨兵，每次启动只通知一次）。** 必须发到登录用户 DBUS 会话（服务常以 root 跑，需显式指定 DBUS_SESSION_BUS_ADDRESS）。此为方案 A 失败兜底。
- 强调：不要硬让服务动态切拓扑/重载模块（会丢设备）。此决策**已落地代码**（2026-09-10）：`install.sh` 新增 `apply_boot_hardening()`（写 `/etc/modprobe.d/sof-es8336-nodmic.conf` 强制 ssp0 无 DMIC 拓扑 + sed 改 UCM BootSequence 加 `Differential Mux=1`），并在 `install_deps` 后调用；`huawei-speaker-mute.sh` 新增 `notify_user`/`wedge_watchdog`/`wedge_watchdog_loop`（检测 dmesg IPC timeout → notify-send 仅通知一次，不重启），启动后台运行、cleanup 回收 PID。`bash -n` 两脚本均通过。**2026-09-10 已实际执行 install.sh**：`/etc/modprobe.d` 落地、UCM 因只读跳过、脚本/服务装新版且 active（验证：service active、已装脚本 grep wedge_watchdog=4、modprobe.d 内容正确、当前 Differential Mux=1）。SKIP_TOPO/SKIP_UCM 可跳过。拓扑待用户重启生效。

## 项目通读对照 + Phase 0 旁路实测（2026-09-10）
- **项目早已定位 jack 冻结根因并写了驱动补丁**：`kernel/backup/README.md` 记「原版 es8316 无 JD 电源域保持 → 拔耳机后 codec deep shutdown（I2C 失联/JD 断电）→ 检测冻结直至重启；中断仅 `TRIGGER_HIGH` 只能检插入、拔出不产生事件」。补丁版=JD 电源域保持+双边沿+去抖+regmap 检查+锁外 I2C。**但补丁导致键盘失效（i8042 IRQ1），已回退**。我的寄存器级分析与其完全一致，并补充：DSDT 里该 `GpioInt` 是 `Edge/ActiveBoth`（驱动写 `TRIGGER_HIGH` 电平本身就错）；codec=ES8336 在 I2C2 双地址 0x10/0x11。
- **脚本版本断层**：`278f673` refactor 把脚本从 856 行砍到 187 行，**删掉了 health_check / jack 死亡告警 / IRQ 卡死保活 / reinit_amp**；文档（REFACTOR_PLAN 等）描述的是旧的 ~728–856 行版本，已过时。当前脚本无 jack 死亡告警。
- **Phase 0 探针实测**（gpio-81 电平 / numid=27 / codec 0x4e、0x4f / es8316 IRQ 计数，插拔 3 轮）：
  - **0x4F 完美镜像插拔**：插入=0x20、拔出=0x24(bit2=`HP_NOT_INSERTED`=1)、带麦/open=0x22，每次都变。
  - **gpio-81 电平恒 `lo`**（脉冲/边沿线，非电平）→ **电平轮询做旁路不可行**（推翻此前设想，也说明 `tools/reg_gpio_watch.sh` 的 gpio 列无信息量）。
  - IRQ 计数正常递增（81→86）。
  - **jack 能"假死"且可自愈**（插拔活动后恢复），与项目"必须重启"的结论不一致——之前的冻结可能源于拓扑/UCM 折腾或为间歇性。
- **结论**：旁路数据源=**codec 寄存器 `0x4F`**（经 `/sys/kernel/debug/regmap/i2c-ESSX8336:00/registers` 读，volatile、走 regmap 锁、安全；**禁止用 gpio 电平**）。轮询 `4f` 解 bit2，跳变即执行切换；作 ALSA jack 的并行/兜底源。局限：codec deep-shutdown 时 regmap 读失败 → 需 Phase 2 驱动补丁。
- **计划**：Phase 0 ✅ → Phase 1 旁路轮询器（用 0x4F）→ Phase 2 驱动补丁（**先只加"JD 电源域保持"单项**，不动 IRQ 边沿，验证键盘是否正常）→ Phase 3 双失声取证。

- **明确不移植历史修复**（debounce / health_check / jack 死亡告警）：那些是"有问题才重构掉的"，加回去后 jack 卡死**反而更严重**。当前 jack 卡死**很少、可忽略**；用户不常拔插、插拔可控。
- **唯一要解决的**：使用一段时间后**耳机 + 扬声器同时失声**；**重启音频服务偶尔能恢复、偶尔不能**。
- 已布取证器 `/tmp/audio_health.sh`（每 20s 快照：`pcm0p` 状态 / jack / codec `0x4f` / 功放 `0x58` / PipeWire 默认 sink；后台 `sudo dmesg -w` 抓 `sof|ipc|es8316|jack|timeout`）→ 日志 `/tmp/audio_health.log`。停止：`pkill -f audio_health.sh`。
- 待判别（复发瞬间）：sink 是否还在、ALSA `aplay -D hw:0,0` 是否成功、`dmesg` 是否 `ipc timeout`/`-110`。
- **用户补充（关键）**：失声时"重启音频服务" = `systemctl --user daemon-reload; restart wireplumber pipewire pipewire-pulse`（**整栈重启**）；**失声时所有音频图标正常，能正常切换耳机/扬声器/HDMI** → **排除 PipeWire/WirePlumber 路由层**；故障在 **pcm0(ES8336) 公共路径**。
- 两类残余假设：**B. codec/DAPM 空闲后未上电**（重开 PCM 重触发 DAPM，有时恢复）；**C. SOF DSP/SSP0 运行态坏（wedge）**（重开无效 → "偶尔不能恢复"）。整栈重启=重开 PCM，"偶尔能恢复"说明多为可被重开修复的运行态（偏 B）。
- **决定性提问**：失声时 HDMI 是否有声？有声→仅 ES8336 路（偏 B）；也哑→DSP 全局（偏 C）。
- **领先假设**：空闲→挂起→resume 抖动（DSP 门控 SSP、codec 掉时钟，唤醒时序出问题）。候选低风险修复：关闭 PipeWire/WirePlumber 空闲挂起（`session.suspend-timeout-seconds=0` / `node.suspend-on-idle=false`，按版本定）。**待拿到一次失声现场(dmesg)再动手**。

## 失声主因指向 S3 休眠唤醒 + 已应用禁止空闲挂起（2026-09-10）
- **用户补充**：**好多次都是系统休眠(S3)后出的问题** → **H1 主假设 = S3 唤醒后 SOF DSP/codec 未正确恢复**（ASoC/SOF resume 或 codec `regcache_sync` 失败 → pcm0 不可用 → 两个都哑）；整栈重启=重开 PCM，"偶尔能恢复"；"偶尔不能"可能是 DSP wedge(H3)。
- **已应用且已验证**（禁止 PipeWire 空闲挂起）：`~/.config/wireplumber/wireplumber.conf.d/51-sof-essx8336-nosuspend.conf` → `monitor.alsa.rules` 匹配 `~alsa_.*sof-essx8336.*`，`session.suspend-timeout-seconds=0`；重启 wireplumber 后 sink 节点该属性="0"。回滚=删文件 + `systemctl --user restart wireplumber`。
- 机制实锤：WirePlumber 0.5.14 `suspend-node.lua`——idle/error 后按 `session.suspend-timeout-seconds`(默认 5s) `Suspend`(关 PCM)；=0 永不挂起。
- **分析+排查+方案已落文档**：`doc/AUDIO_SILENCE_ANALYSIS.zh-CN.md`（事实 / 假设 H1-H3 / 判别法(失声时 HDMI + dmesg(ipc timeout/-110)) / 取证器 / 一次性取证命令 / 方案 S1-S4 / 回滚）。
- 下一步候选：**S2 = 休眠恢复钩子自动重启音频栈**（`/usr/lib/systemd/system-sleep/` post-suspend 以桌面用户 `systemctl --user restart wireplumber pipewire pipewire-pulse`）；根治 = S4 更新 `linux-firmware`/内核。
