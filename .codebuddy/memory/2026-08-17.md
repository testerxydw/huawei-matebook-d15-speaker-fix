## 当前脚本真实架构（与文档需一致）
- **DMI 自动判定 GPIO 策略** `detect_dmi_gpio_needed`：`BoF*` → `NEEDS_GPIO=0`（BIOS 已接管功放 GPIO，用户态不碰，否则功放 I2C 永久失效）；`BOD*`/`BOH*` → `NEEDS_GPIO=1`（用户态 gpioset 拉供电）。
- **三级插拔监听**：① Python 监听 `sof_es8336` input 事件（`SW_HEADPHONE_INSERT`）+ 周期轮询（`POLL_INTERVAL`，默认5s）；② `alsactl monitor hw:0`；③ 每 2s 纯轮询兜底。
- **健康检查** `health_check`：每 `HEALTH_CHECK_INTERVAL`（默认60s）校验 gpioset 存活 + 功放 `0x01` 寄存器合法值（`0x00`插/`0x69`拔），异常自动恢复。
- `reinit_amp` 写入后读回 `0x01` 验证，失败重试（最多3次，NEEDS_GPIO=1 时重启 GPIO）。
- **python3 为必需依赖**（DSDT 解析 `detect_gpio` + input event 监听 `jack_monitor`），非可选。
- 诊断脚本已移入 `tools/`（`jack_watch.py`/`pure_poll.py`/`event_sync_test.py`/`reg_watch.py`），`.gitignore` 忽略 `*.log`。

## R6 实施与 R2 调查（插拔检测失效根因）
- **R6 已提交** `042a755`：unplug_volume_guard 的 3 次 runuser 会话收敛为单次（`set_pw_vol` 内循环 3 次 wpctl；ALSA 层清零仍 3 次）。已部署 /opt 实测通过，未推送（等用户统一推送）。
- **R2 调查触发真实问题**：用户报"R2 后监控不到"。实测排除脚本责任：
  - 回退 R2 到纯 R6 后，独立每 2s 采样 ALSA 仍全程 `jack=on` 无跳变 → R2/R6 无关。
  - `PipeWire` 重启无效（PipeWire 仅消费 jack 控件，不产状态）。
  - **内核 /dev/input/event10 原始字节监听 25s 窗口：插拔零 SW_HEADPHONE_INSERT 事件** → jack 检测在更底层（内核/声卡）已死。
  - 双控件 `numid=27(Headphone)=on / numid=28(Headset Mic)=off` 同时卡死（均不随插拔翻转）。
- **根因定位（关键）**：BoF-XX 的 DSDT/ACPI **独占 `speakers-enable` / `headphone-enable` GPIO**（BIOS/EC 管理）。内核 SOF 驱动 probe 时也申请这些 GPIO → `EBUSY`，card0 注册失败。此为内核/ACPI 层冲突，**用户态模块重载无法清除**。
  - 尝试 `modprobe -r snd_soc_sof_es8336`（仅 machine 驱动）→ 失败（/dev/snd 被 pipewire 占用，refcnt=4）。
  - 停 pipewire+禁 socket 后 `modprobe -r snd_soc_sof_es8336` 成功，但重载后因 headphone-enable GPIO EBUSY 未注册 card。
  - 进一步 `modprobe -r snd_sof_pci_intel_tgl`（顶层 PCI，级联释放整链）成功，重载后错误变为 speakers-enable GPIO EBUSY，**card0 仍未恢复 → 当前 `no soundcards`，音频完全失效**。
  - `gpioinfo` 已看不到这些 GPIO 的占用者 → 冲突在 ACPI/固件层。
- **现状（2026-08-17 末尾）**：音频因我的重载实验失效，需**整机重启**恢复。jack 检测原死亡（07:44–11:22 正常，之后内核不发 SW 事件）根因是 SOF/ACPI GPIO 冲突导致声卡栈不稳，非脚本问题。
- **新需求（用户提出）**：将"jack 检测软恢复（不靠整机重启）"作为项目新需求设计。已写 `JACK_RECOVERY_DESIGN.zh-CN.md`（含 P1–P5 原语可行性门控、Q1/Q2 开放问题、§6 相邻问题）。
- **Q1 实验（14:35）决定性失败**：PCI remove(0000:00:1f.3)+rescan 后 card0 仍无，dmesg 报 `headphone-enable GPIO EBUSY`(error -16)。→ P2 与 P1 同源证伪：`speakers/headphone-enable` GPIO 被 **ACPI/BIOS 持久独占**，模块卸载与 PCI 重枚举都不释放。**任何内核态重载驱动都无法软恢复声卡，唯一恢复手段是整机重启**。

## 重启后确认与相邻问题
- **整机重启后 jack 检测已恢复**：`amixer -c 0 cget numid=27` 插拔正常 `on↔off` 翻转 → 印证"运行期死亡"是临时态，随重启恢复，非永久硬件故障。jack 软恢复需求仅在运行期死亡时有意义。
- **相邻问题1**（开机首次拔耳机偶切 HDMI）：WirePlumber 默认路由策略（扬声器 sink 未就绪时回退 HDMI），非脚本行为；脚本只动 I2C 静音+音量，不改 sink 路由。属 PipeWire 配置问题，独立于本需求。
- **相邻问题2**（拔插时音量设0有延迟）：`unplug_volume_guard` 3次 `wpctl set-volume 0` + 0.25s 间隔，总约0.75s，是**故意防爆音**（压过 WirePlumber 端口恢复竞态）。R6 只合并 runuser 会话、不改总时长。延迟为必要代价，非 bug。
- **末尾连续 on/on/off（澄清）**：用户是在"插入后"才手动敲 amixer 查看，故先一串 on 拔出才翻 off，属手动采样时序，**非 jack 抖动**；jack 检测当前完全正常。已更正设计文档 §6.4。

## jack 检测运行期死亡：已从偶发升级为可复现必现（核心根因）
- **复现规律**：开机后一段时间正常，之后内核停止发耳机插拔事件。本次重启(14:41 boot)后约 6 分钟死亡（上次是数小时后），**必定复现**。
- **死亡证据**：`/dev/input/event10` 节点存活(`sof-essx8336 Headset`)、内核原始字节监听零 `SW_HEADPHONE_INSERT` 事件、ALSA `numid=27` 卡死 `on`、脚本服务最后反应 14:47:14 之后无反应。
- **本轮 dmesg 无 SOF IPC -5 错误**（启动干净）→ 死亡与 SOF 固件报错无直接关联；是内核侧 codec/jack-detect 路径停止产出（设备节点在、事件与 ALSA 控件双冻结）。
- **含义**：jack 检测死亡是真正根问题，使现有脚本插拔联动静音 + 想验证的"静音替代置0"方案（无 unplug 事件则不触发）全部失效。
- **软恢复不可行（已证）**：P1 模块重载 / P2 PCI remove-rescan 都因 ACPI 独占 speakers/headphone-enable GPIO(EBUSY) 失败，唯一恢复=整机重启。
- **静音方案验证被阻塞**：本次 mute 测试(mute_test.sh)因真实脚本服务并发运行、拔耳机瞬间脚本 volume-guard 覆盖测试静音而污染结果（非监控坏）；干净验证需先停脚本服务单独测 WirePlumber 是否在 jack 事件取消静音——但 jack 检测先死了，静音方案暂无法验证。
- **待解决 Q2（根因触发器）**：死亡瞬间的诱因（suspend? 某应用? 时序?）未抓到。下一步建议后台常驻捕获 dmesg+input 事件，死亡时比对诱因；或评估 P4(用户态读 jack 检测 GPIO，libgpiod 可用，但需确认 jack-detect GPIO 线号且未被 ACPI 独占)。
